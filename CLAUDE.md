# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Beyond the Dialogue is an Electron desktop to-do app (an "AI-native work board") whose AI features are powered by an **embedded agent runtime** (the Pi coding-agent SDK, `@earendil-works/pi-coding-agent` / `@earendil-works/pi-ai`, pinned exact versions). It is a **type engine**: every task carries a workflow Type (the seeded built-ins are `plain` and `document`, plus user-defined Types stored in a `task_types` registry), and the Type **declares** what happens — its **family** (`'document' | 'working-system' | 'coding'`, declared once in `src/core/domain/family.ts`; a Type with no family needs no assistance), its declared inputs, its assistant instruction (`aiGuidance`), and its **finish behaviour** (one of `complete-only | file-as-is | polish-then-file | deposit-then-curate`) together with an **output destination**. Behaviour is dispatched on those declarations, never on a hardcoded Type name or key comparison. Feature 002 lit the first assistance family, **Document**: the user writes in the task's working area (the task note, re-argued as the draft), Finish offers "organize & file" or "file as written" (the declaration sets the default), every task holds durable **conversations** grounded in its own material, and a wiki-destined Type **deposits then curates** a user-owned knowledge base following the LLM-WiKi pattern (the guide is bundled at `src/main/wiki/LLM-WiKi.md` and seeded create-only into each collection) — with an **undo** that reverses the curation and never the deposit. The POC's category engines (pre-process, suggestion chips, learning/jira/meeting kinds) are **deleted**; their database rows are preserved as history. Grants are structurally inert in this milestone (no Type declares one). Feature behavior is specified under `specs/` using the Spec Kit workflow (`.claude/skills/speckit-*`), governed by the project constitution at `.specify/memory/constitution.md`.

## Commands

```bash
npm run dev          # electron-vite dev server + Electron
npm run build        # electron-vite build (outputs to out/)
npm run typecheck    # tsc --noEmit -p tsconfig.node.json && ... -p tsconfig.web.json
npm test             # run all tests: tsx --test test/**/*.test.ts
npm run dist         # build + electron-builder (outputs to release/)
```

**`typecheck` names both projects explicitly, and must keep doing so.** The root
`tsconfig.json` is a solution file (`"files": []` plus `references`), and `tsc --noEmit`
against a solution file compiles **nothing** — referenced projects are only built with
`-b`. It silently passed for the life of the repo while ~11 real type errors sat in the
tree. If you change this script, verify it still fails on a deliberate error.

- Tests run **headless** (node:test + tsx) — no Electron is launched, and no network/API key is needed. They import `src/main` modules directly.
- Single test file: `npx tsx --test test/core.test.ts`; filter cases with `--test-name-pattern="..."`.
- Runtime requires Node ≥ 22 (uses the built-in `node:sqlite`). `.npmrc` points at the npmmirror registry and electron mirror — leave it alone.

## Git workflow

GitHub Flow: `main` is the trunk; development happens on short-lived branches cut from its
HEAD, and changes reach GitHub only through a PR into `main` — never commit into a
checked-out `main`, never `git push origin main`. Landed PRs use merge commits, never
squash: the individual commit messages are the record. Commit finished, verified work
before switching context.

## Architecture

### Process layout & IPC

Standard electron-vite split: `src/main` (Node), `src/preload` (contextBridge), `src/renderer` (React 18), plus `src/shared` and `src/core` imported by all three. Layer order is `shared → core → main adapters → hosts`.

**`src/core` is the domain and application layer, and it performs no I/O.** It holds `domain/` (pure rules — `family.ts` = the single declaration of the family set (a leaf module), `finish.ts` = the four finish behaviours + the organize step and its `verifyPolish` bound, `destination.ts` = the destination-store set + resolution + confinement, `grant.ts` = grant resolution + egress + propose/confirm, `chatContext.ts` = declaration-built conversation grounding (two first-class cases: document-family and family-less), `validation.ts`, `taskType.ts`, `slug.ts`, `workingArea.ts`, `plugins.ts`, `config.ts`), `i18n/` (the message catalog every layer reads — see Language below), `services/` (`finishService.ts` = the finish mode machinery, `conversationService.ts` = the stored-turn conversation use cases, `taskService.ts`, `settingsService.ts`), and `ports/` (the interfaces services depend on — `storage`, `conversations`, `artifactStore`, `agent`, `notifier`, `clock`, `paths`). It must not import `electron`, `node:*`, or a DOM global: it is compiled into the **main** target *and* the **renderer** target, and `test/layering.test.ts` asserts the boundary mechanically (along with "renderer imports nothing from `src/main`" — both the `from '…'` and the bare side-effect import forms). If you need I/O in core, add a port and implement it under `src/main/adapters/`. **The conversation service receives no task port** — a conversation can never act on the board (FR-010), structurally.

Inside the other layers modules are grouped by domain. `src/main`: `index.ts` is the composition root (it builds adapters, builds services, registers the transport); root also holds the shared machinery (`paths.ts`, `db.ts`, `tasks.ts`, `job-queue.ts`, `types.ts` = db-bound wrappers over the core domain rules, `alarms.ts`, `plugins.ts`); `adapters/` = the port implementations (`sqlite/storageAdapter.ts` + `sqlite/conversationStore.ts`, `artifacts/` = `wikiStore.ts` + `folderStore.ts` + shared `deposit.ts`, `agent/sessionAdapter.ts`, `notifier.ts`, `paths.ts`); `ai/` = agent runtime + config + session factory + the per-turn chat runner (the Pi-SDK seams); `wiki/` = `wiki.ts` + `vault.ts` + the `ingest` job handler + `undo.ts` (the curation undo — a code operation, no session). Renderer components live under feature folders: `components/board/`, `components/focus/` (task band + the working-area editor + the stored-conversation `ChatPanel` + `RemoteProposalBar`), `components/overlays/` (drawer views, command palette, welcome, Settings), `components/ui/`; renderer-only helpers live in `src/renderer/src/lib/` (e.g. `typeCatalog.ts`).

- **`src/shared/types.ts`** — every domain type (Task, List, Settings, JobRecord with its `StoredJobKind` read-boundary honesty, IngestRecord with `snapshotDir`/`undoneAt`, TaskTypeDef with its `family`/`finishBehaviour`/`destination` and **no grants field** (D9 — grants are storage-only), Conversation/ConversationMessage, FinishMode/FinishReport, `Destination`, `PluginGrant`, AppSnapshot…). `src/shared/ipc.ts` — channel names, the `RendererApi` interface, **and the typed `AppCommands`/`AppEvents` maps**: every command's args+result and every event's payload, keyed by channel. Feature 002's contract events use the contract's own names (`artifacts.filed`, `conversation.updated`, `conversation.delta`). `broadcast` in the main process is typed by `AppEvents`, so a payload that drifts from the renderer's expectation is a compile error rather than a runtime surprise on one host. **Adding a feature means touching types + IPC channels + preload + main handler + store in lockstep.**
- Main process entry `src/main/index.ts` wires everything: open DB → migrate → ensure vault → JobQueue with **one** registered handler (`ingest`, and only while the assistant switch is on) → IPC handlers → window. Handlers persist, then `broadcast()` the change event (typed); the renderer merges events into its `AppSnapshot`.
- Renderer: single `AppProvider` context in `src/renderer/src/store.tsx` holds the snapshot and subscribes to all events. Views are `my-day | list | activity | settings`.

### Persistence split

Four storage kinds, deliberately different:

1. **SQLite** (`node:sqlite`, *synchronous* `DatabaseSync`) at `<userData>/app.db` — lists, tasks (with `inputs` JSON + `alarm_at`; the retired `preprocess_status` column survives as history), `task_types` (the Type registry, seeded with the **2** built-ins `plain` + `document`, each row carrying `family`/`finish_behaviour`/`destination_json`/`grants_json` — grants always the empty default, storage-only), `enrichment_jobs`, `task_notes`, `task_conversations` + `conversation_messages` (feature 002: durable conversations, cascade-deleted with the task; assistant messages store their `usage_json`), `ingest_ledger` (with `snapshot_dir` relative to the collection, and `undone_at`), `settings` (incl. the `skills`/`mcpServers` JSON arrays), and the history tables `task_preprocess` + `suggestions` (rows preserved, **no accessor reads or writes them** — D4). Schema lives in `src/main/db.ts` (`SCHEMA` const, `migrate()` steps under `schema_migrations` — v3 is the v0.8 rebuild, **v5 adds the declared workflow**, **v6 reconciles task inputs against declared schemas**, **v7 retires the per-task skill/MCP placeholder inputs**, **v8 moves the wiki location out of `settings.wikiPath` and into each wiki-destined type's `destination.rootPath`** — a value the user had configured is copied into those destinations before the row is deleted; one that was never set is deliberately NOT materialized as the old `~/Documents/WorkBoard-Wiki` default; **v9 rewrites the `settings.mcpServers` row from the old stdio `transport` envelope to the standard `{name, config}` shape** — idempotent, entries already carrying `config` pass through; **v10 (feature 001) moves every secret OUT of the settings table** — the provider key and each MCP `config.env` lift into `<userData>/pi-agent/secrets.json` (mode 0600, machine-fingerprint-gated, `src/main/secrets.ts`) leaving presence (`hasApiKey`; the plaintext `apiKey` row is deleted on migration and on every save), and the POC's plaintext mirror in the SDK's own `auth.json` is stripped, **v11 rebuilds `tasks` to make `list_id` nullable and add `background`/`target`** (same gated-rebuild + `PRAGMA foreign_keys` discipline; FR-006 deleting a List now UNASSIGNS — `deleteList` sets `list_id = NULL`, never cascades), **v12 adds `task_attachments`** — attachment rows whose `path` is relative to the data-folder root only, **v13 (feature 002) is the vocabulary migration** — rebuilds `task_types` (`kind` → nullable `family`, CHECK mirroring `family.ts`), deletes the `learning`/`jira`/`meeting` built-ins, maps user Types by the D11 rule (`learning→document`, `jira→working-system`, `meeting→document`, declarations kept), re-homes tasks of deleted built-ins to `plain` with content byte-identical, and drops the retired `tasks.type` CHECK (it was live and blocked both the `document` key and user-defined keys), **v14 adds the conversation tables** (cascade-delete with the task — deletion is final), **v15 extends `ingest_ledger`** (`snapshot_dir`, `undone_at`, state CHECK widens to include `'undone'`) **and drops the retired category CHECK on `task_preprocess`** — dropped, not restated: the history rows hold exactly the retired values — all following the same `ran(v)`/`mark(v)` ladder), row mappers map snake_case columns → camelCase domain types. Soft deletes via `deleted_at` tombstones.
   - **v5 rebuilds three tables** (`tasks`, `task_types`, `task_preprocess`) to widen a SQL `CHECK` — SQLite cannot `ALTER` one. The `tasks` rebuild **must** wrap the swap in `PRAGMA foreign_keys = OFF` / `finally { PRAGMA foreign_keys = ON }`: it has live child rows and the drop fails immediately otherwise. Each rebuild is gated by detecting the old constraint in `sqlite_master.sql`.
   - **Removing a declared input field requires a migration that strips it.** `validateInputs` rejects an undeclared key on *every* write, so a task left holding one cannot be edited or finished and the user sees `unknown input "..."` with no way to act on it. v4 did this by name for `link`; v6 generalized it (`reconcileInputsForType`, also called on every type save); v7 reused it to retire the per-task `skill`/`mcp` placeholders. Follow the same shape for the next one.
   - **The SQL `CHECK` literals necessarily restate the family set** (SQL cannot reference a TypeScript constant). That is the unavoidable-hardcoding exception to the constitution's dispatch-by-declaration rule (Principle I), so each restatement carries a comment naming `src/core/domain/family.ts` as the declaration it mirrors — and `test/family.test.ts` asserts the mirror mechanically (quickstart drill #1: add a fourth family without the mirror and it goes red). Change one, change both.
   - **Old migration steps must recognize the new shape.** The ladder walks every step on a fresh database too: steps written against retired columns gate on the stored DDL or `PRAGMA table_info` (v4 checks for the `kind` column; v5's rebuild gates name the OLD marker, not merely the absence of `'meeting'`; v3's customTypes import inserts `family` when the table is already family-shaped). A step that queries a column the current SCHEMA no longer has crashes every fresh install.
2. **Application-owned files under `<userData>`**: `vault/` (existing) plus `attachments/` (feature 001 — `attachments/<attachmentId>/<name>`, copied IN at add time so the original moving or dying never breaks a task; `src/core/ports/attachments.ts` + `src/main/adapters/attachments.ts`; deletion of the task is final: rows and files purge together) and `pi-agent/secrets.json` (the machine-bound secret store; `machineFingerprint` = hostname + username — never the POSIX uid, which is unavailable on Windows; a folder copied to another machine reads every value as ABSENT and re-asks). The whole folder is the board: no board table may store an absolute path (`isRelativeStoredPath` is the rule; `test/portability.test.ts` is the scan).
3. **Vault files** under `<userData>/vault/` — the working area's draft is born as a file: `notes/<taskId>.md` mirrors the `task_notes` row (the same storage the POC's learning notes used; feature 002 re-argues it as the Document draft — D3, no new store). All paths come from `src/main/paths.ts` (never hardcode; `setUserDataRoot()` redirects everything for tests).
4. **The knowledge base (wiki)** — a markdown directory the TYPE destined for it declares (there is no global wiki setting and no built-in default; a destination with no location is refused at Finish with `destination.notConfigured`): `raw/` (immutable deposits — outside the audit walk, which is what makes "undo never rolls back the deposit" structural), `wiki/` (agent-authored pages), `learning-notes/` (curated notes by default), `index.md`, `log.md`, `CLAUDE.md` (the **wiki schema**, app-authored from `WIKI_SCHEMA` in `src/main/wiki/wiki.ts` — distinct from this repo file), `LLM-WiKi.md` (the pattern guide, seeded create-only from the bundled `src/main/wiki/LLM-WiKi.md` template), `.history/<run>/` snapshots (one per curation; the ledger's `snapshot_dir` names it, relative to the collection).

**Artifact destinations are declared per type, not fixed app-wide.** Each type carries a `Destination` (`store: 'wiki' | 'folder'`, an absolute `rootPath` — required for both stores, so `store` says what happens at write time, never where the path comes from; **an empty `rootPath` is legal only on the seeded built-ins** (the generic Document Type ships without a location — Q1 — and its first Finish is the guided refusal), while a saved USER Type with an empty root is refused at SAVE (FR-013, `validation.destinationNeedsRoot`) — and a relative `subdir`), resolved through one confinement check (`relative()` + not-`..`-prefixed + not-absolute — there is deliberately only ONE implementation). A location that is gone at finish time refuses with `destination.unreachable`: never half-filed, never a substituted location. The store is chosen by `store`: `src/main/adapters/artifacts/wikiStore.ts` (establishes the pattern's minimal structure **create-only** at the first destined finish — D6: setup belongs to first use, never at app start, and structure the user changed is never rewritten) or `folderStore.ts` (a plain folder the user owns — it **never scaffolds**). **Collisions never overwrite or move**: `distinctName` writes `name-2.md` alongside.

### Job queue (the core machinery)

`src/main/job-queue.ts` — `JobQueue` is a persisted, concurrency-limited executor (max from settings, default 2) over `enrichment_jobs`. **One registered kind** since feature 002 (D4):

- `ingest` (`wiki/ingest.ts`) — hosts the `deposit-then-curate` curation run (see below). Registered ONLY while the assistant switch is on — registration itself is the reachability.

The retired `preprocess` and `suggestion` kinds are deleted: their handlers, per-category instruction registries, on-add triggers and renderer surfaces are gone, and **no board interaction enqueues any job any more** (`taskService` mutation outcomes carry an always-empty `enqueue`). Their stored rows are history: no accessor reads them, and `requeueInterrupted()` **skips kinds with no registered handler** — a retired row stuck in `running` keeps the state it was written in, never re-run and never rewritten. `JobRecord.kind` reads back as `StoredJobKind` (`JobKind | 'preprocess' | 'suggestion'`) — the legacy values are tolerated at the row-mapper boundary rather than lied about in the narrow `JobKind = 'ingest'` union.

Key behaviors: transient failures (`rate limit`, `timeout`, `5xx`, `429` — see `isTransientError`) auto-retry with exponential backoff up to 3 attempts; `requeueInterrupted()` re-enqueues stuck jobs of registered kinds at startup; progress/step labels are emitted as events and shown in the renderer. The `ingest` job runs on Finish for `deposit-then-curate` types only.

### Finish (the behaviour the type declares)

`src/core/services/finishService.ts` is the ONE place a task's completion is decided. It dispatches on the type's **declared** `finishBehaviour` via `FINISH_STRATEGIES` (`src/core/domain/finish.ts`) **and on the MODE the user chose** (feature 002, D8): `tasks:finish` carries `{ taskId, mode?: 'assisted' | 'as-written' }`; `defaultFinishMode` reads the declaration (organize-capable → assisted, everything else → as-written) and `resolveFinishMode` forces `'as-written'` while the switch is off or no model is configured — **no session is constructed at all** in that state, and feature 001's `assistant.disabled` finish refusal is deleted (the board never blocks on AI). The ordering is load-bearing: **validate inputs → blank-draft refusal (`document.empty`, the task stays active) → resolve + confine the destination (blank root → `destination.notConfigured`; gone → `destination.unreachable` from `prepare()`) → write → mark complete, clear alarm → report**. The result is the contract `FinishReport`: `{ ok, artifact?, path: 'organized' | 'as-written' | 'deposited', assistantStep?: 'ran' | 'skipped' | 'failed' }` — where the copy went and which path ran. A finish that cannot succeed must fail while the task is still actionable, so nothing is marked complete until the artifact step has succeeded. `deposit-then-curate` is the exception by design: it deposits synchronously (the part that must survive), marks complete, and hands the long curating agent to the `ingest` job — `runIngestJob` calls the same `depositThenCurate` strategy with `priorDeposit` (the files the finish already deposited, reported not repeated), and the strategy snapshots AFTER the deposit, then curates: **the order is load-bearing (D7) and pinned by test** (drill: move the snapshot earlier and `test/knowledgeBase.test.ts` goes red).

- **`polish-then-file` is the generic ORGANIZE step** (D2 — the behaviour keeps its name; a comment records the re-argument). The instruction that drives it is the Type's declared `aiGuidance`, not a meeting-minutes template; the meeting-only action-items append is deleted. The bound is checked: every fact the assistant reports must be traceable to the user's own words (`verifyPolish`), or the draft is filed AS WRITTEN and the step reported failed. The honest limit is documented at `verifyPolish`: it catches *asserted* content, not a fabrication buried in undeclared prose.
- Every behaviour degrades rather than failing: off, unconfigured, or a failed assistant step, the user's content is still filed as written, the task completes, and the report plainly says which step did not run (`assistantStep: 'skipped' | 'failed'`). A finish never fails solely because AI is unavailable.
- A blank working area refuses (`document.empty`) before the destination is even resolved; a deposit with an attachment still has material and proceeds.

### Agent runtime seams (critical for tests)

All Pi SDK usage is isolated behind a handful of modules:

- `src/main/ai/agent-runtime.ts` — thin adapter: one shared `ModelRuntime` with app-private `auth.json`/`models.json` under userData (never the user's `~/.pi`); `streamChat` returns the reply WITH the provider's usage metadata (the stored assistant message must carry it — see chatMessages below).
- `src/main/ai/session-factory.ts` — central `createJobSession()` factory building per-job in-memory agent sessions (system prompt, tools, cwd). It exposes **test seams**: `setSessionFactory()` and `setSimplePromptOverride()` replace the Pi SDK entirely with scripted sessions. `src/main/adapters/agent/sessionAdapter.ts` implements `AgentSessionPort` over it. `src/main/ai/chat.ts` is the conversation turn runner: ONE short-lived stream per turn (`runChatTurn`, injectable stream fn), built from the stored history plus the grounding, retaining nothing — the in-memory per-panel ChatSession transcript is deleted (D5).
- `src/main/ai/chatMessages.ts` — the shape a chat history must have before the SDK sees it, and deliberately **SDK-free** so a test can pin it (`test/chatMessages.test.ts`). An assistant entry without a `usage` makes the SDK's context estimator throw *inside* the provider call, which the SDK reports as an error terminal message with no content — i.e. a chat reply that silently never appears. `streamChat` applies it at the call.
- `src/main/adapters/agent/mcpAdapter.ts` — the **only** file allowed to name `pi-mcp-adapter` (guard test enforces it); loaded through `jiti` because the package entry is TypeScript-only. Builds the isolated in-memory config from an already-resolved grant; `setMcpAdapterFactory()` is the test seam. See the MCP bullet in Conventions for the full contract.

**Grants are resolved HERE, at session build, from the run's PURPOSE** (`resolveGrant` in `src/core/domain/grant.ts`). `purpose: 'confined'` returns `NO_GRANT` unconditionally — every assistant step feature 002 runs (organize, curate, converse) is confined, so the guarantee holds even for a misconfigured caller. `purpose` defaults to `'confined'`, so a caller that says nothing gets the safe answer. **Grants are structurally inert in this milestone (D9/FR-015):** `TaskTypeDef` has NO grants field, `types:save` persists the empty `grants_json` default whatever a payload carries, and the Type editor shows no grants control — "a checkbox that changes nothing tells the user something untrue about their control." `resolveGrant`/`buildSessionContext` keep an explicit `grants` parameter for the later feature that re-adds the declaration; nothing can supply it from a Type today. Granted skills load through the SDK's `additionalSkillPaths`; note the SDK does **not** enforce a skill's frontmatter `allowed-tools`, so a skill is a capability and never a permission.

**Conversation grounding is a total registry over TWO first-class cases** (`src/core/domain/chatContext.ts`): document-family tasks (the note is presented as the working-area draft) and family-less tasks (title/background/target/declared inputs/note). Chat attaches to EVERY task (FR-008), so the family-less case is an entry, not an absence — the 001 lesson (the added `meeting` category silently got less grounding) made structural. Not-yet-live families get the family-less treatment. The grounding is built from declarations: task title, background, target, the Type's **declared** inputs (an undeclared key never rides along), and the working-area note. `test/chatContext.test.ts` asserts totality over every family value including null (drill #2: remove the family-less entry → red).

**The egress boundary is enforced at context CONSTRUCTION, not at the tool boundary** (`buildSessionContext` in `grant.ts`, wrapping the grounding in the conversation service). Once a session can reach an external tool, filtering at the call site is too late — the content is already in the prompt. A granted session therefore sees only the task's declared inputs and the user's request; an ungranted one sees exactly what it always saw.

**Remote changes are structurally un-makeable without confirmation.** `remoteToolSurface()` exposes only a *proposal* tool; the mutator (`RemoteMutator.apply`) is reachable only from the application after a per-change confirmation, never from the model's tool surface. Making the operation unreachable is what makes confirmation a structural constraint rather than a prompt instruction — the constitution's Principle II rule that a model's compliance is never a control. Proposals surface in `RemoteProposalBar`, which shows the literal payload before the user confirms.

Tests never contact a real provider: they inject scripted sessions (`test/e2e.test.ts` is the flagship: idea → Document task → draft across a simulated restart → finish organized → knowledge-base curation → Activity ledger → undo → re-finish as-written, all scripted, with the off-state segments asserting zero seam invocations). `ai-config.ts` (in `src/main/ai/`) is pure and importable anywhere — the renderer uses it for the "AI not configured" indicator. Keep Pi SDK usage out of any file that isn't one of the seams above.

### Knowledge base: deposit first, curate second, undo the curation only

On Finish of a wiki-destined Type: synchronous file-copy of the working-area draft (filename = title slug, deduped) + the optional attachment into `raw/<taskId>/` *first* (survives any later failure — no AI summary joins it since D4), the task completes, and the curation is enqueued. The background `ingest` job re-enters the SAME `depositThenCurate` strategy with `priorDeposit`: snapshot the collection into `.history/<timestamp>/` (recorded in the ledger's `snapshot_dir`, **relative** to the collection) → run the confined agent (tools `read|write|edit|grep|find|ls`, **no shell**, cwd = the collection root — the confinement is the tool surface, not a prompt line; must follow the wiki `CLAUDE.md` workflow and write the curated note at the task's learning-note path, default `learning-notes/<slug>.md`) → diff against the snapshot (`diffTouchedFiles`) to report what was actually touched in the ledger (shown in the Activity view, where failed runs retry). The snapshot-after-deposit order is load-bearing (D7) and pinned by test. Assistant off → the deposit stands alone and the report says the curation did not run; unconfigured → the job fails honestly with the deposit intact. A learning-note path that no longer resolves under the declared destination is refused at Finish, never silently mis-saved. Never delete or restructure the scaffolding logic — scaffold is create-only, at the first destined finish (D6).

**Undo** (`src/main/wiki/undo.ts`, `wiki:undoCuration`): a pure code operation on user-owned files — no session, no model. It restores exactly the run's touched files from that run's OWN snapshot (a file the curation created returns to absence), never rolls back the deposit (`raw/` is outside the audit walk — structural, not conventional), moves the ledger `done → undone` with `undoneAt`, and refuses in codes: `undo.notDone`, `undo.snapshotMissing` (report it, do not guess), `undo.destinationUnresolved` (the same resolution rule as at finish — never mis-restore). Two runs touching one page keep their own retained states; the result names which state it restored. The Activity view offers undo on `done` rows and is NOT assistant-gated: reversing history does not depend on the switch.

### Language (the UI is bilingual)

Every string the app's own UI shows comes from a catalog in `src/core/i18n/` — `en.ts` is the key set, `zhCn.ts` must cover it, and the renderer reads it through `useT()` (`src/renderer/src/lib/useT.ts`), which is fed by `Settings.uiLanguage` in the store. A missing translation or a stray key is a `tsc` error, so `npm run typecheck` is the parity gate.

- **`uiLanguage` is presentation only.** It is named that way to say so: it never reaches a prompt, and the agent's output language is the model's own. The one `toLocaleString('en-US')` left in `src/main` is inside a prompt and carries a comment saying why.
- **The English values are the app's original literals, character for character.** Two things depend on it: `displayTypeLabel` and friends decide a seeded type label is still the default by comparing the stored row against `en[key]` (so a rename is never clobbered — no migration, nothing written back), and it keeps the change invisible in English. Translating a literal into a key may only turn interpolation into a `{param}` hole.
- **The domain refuses in codes, not sentences** (`src/core/i18n/issues.ts`). `src/core` has no language and is compiled into both hosts, so `validation.ts`, `destination.ts`, `plugins.ts` and the finish/conversation services return `MessageIssue[]` / throw `LocalizedError`. Main phrases them in `handleCommand` (`src/main/index.ts`) before the throw — errors cross IPC as strings, so nothing structured survives the boundary. Feature 002's refusal codes: `destination.notConfigured` (the contract's `destination.not_configured` — keys are dotted lowerCamelCase, enforced by `test/i18n.test.ts`), `destination.unreachable`, `document.empty`, `conversation.emptyMessage`, `undo.*`. `localizeThrown` passes non-code errors through **by identity**, which is what keeps a transient job failure retriable.
- **Main and core thread the language as a parameter** from the call sites that already hold `Settings` — never a module global. Step labels are produced already-localised because `jobs.step_label` persists them.
- **The drift guard** (`test/i18n.test.ts` + `test/i18n-literal-baseline.json`) fails when a new user-visible literal appears outside the catalog. The baseline is now empty and the ratchet is strict; `npx tsx test/helpers/i18nBaseline.ts` regenerates it, and its diff should only ever shrink. Its census sees JSX text and the `placeholder`/`title`/`aria-label`/`alt` attributes — **not** strings passed as arguments (`notify('…')`, a `confirm({ message })`), so grep for those when adding a feature.
- **Known limits, by design:** `jobs.step_label`, the retired `tasks.preprocess_error` column and the ingest ledger keep the language they were written in — a record of what happened, in the language it happened in. Stored conversation messages keep their language too (the model's own). The agent SDK's own step labels (tool names, "Thinking…") cannot be localised and appear in English mid-progress.

## Conventions & gotchas

- **`node:sqlite` is synchronous** — no awaits around DB calls anywhere in main.
- CamelCase domain types everywhere; only `db.ts` row mappers know the snake_case columns.
- ESM-only packages (Pi agent SDK) are loaded via dynamic `import()`; main builds to ESM (`out/main/index.mjs`) but preload stays CJS.
- Job handlers must throw with a message `isTransientError` understands for retries; use `ctx.setStep(label, progress)` for renderer progress. The one live trigger: `ingest` on Finish of a `deposit-then-curate` Type. No board interaction (My Day add, edit) starts any AI work.
- The retired `preprocessStatus` column and its stored values (`none → queued → running → ready | failed`) are history: nothing sets or reads them; new tasks carry `'none'` by column default only.
- Behavior dispatch always goes through the Type's **declarations** (`effectiveTypeDef` in `src/main/types.ts` reads them; `effectiveType`/`effectiveFamily` in `typeCatalog.ts` renderer-side) — never a type key, never a family-name comparison outside the declared registries (`workingAreaFor`, `chatCaseFor`, `FINISH_STRATEGIES`). User-defined Types are full citizens: identical declarations behave identically to built-ins (FR-012, pinned by `test/userTypes.test.ts`).
- Conversations are storage, not memory: order comes from `rowid`, a failed send keeps the stored history intact, and the assistant message stores its provider usage (`usage_json`) — an assistant entry without usage makes the SDK's context estimator throw inside the provider call (`chatMessages.ts`).
- MCP support is LIVE: `McpServerEntry` is `{ name, config }` where `config` is the **standard `mcp.json` server object** (command/args/env/cwd, url/headers, adapter options) — added manually by pasting JSON in Settings (`parseMcpJsonPaste` in `src/core/domain/mcpConfig.ts`), validated structurally only (`validateMcpServerConfig`; everything else passes through uninterpreted), migrated by v9 from the old stdio `transport` envelope. The rows are the source of truth; `src/main/mcpConfigFile.ts` rewrites `<userData>/pi-agent/mcp.json` (standard shape, deterministic) on every save and at startup as an **output-only** inspection copy nothing reads back. Transport: `pi-mcp-adapter@2.35.0` (exact-pinned; its published-npm `@modelcontextprotocol/{client,core}@2.0.0` deps clear the reproducibility gate that deferred 2.33.0 — `test/mcpAdapter.test.ts` re-runs that gate on every test) is built at the `session-factory.ts` seam from the **already-resolved grant** via `src/main/adapters/agent/mcpAdapter.ts` (`buildMcpExtension`, seam `setMcpAdapterFactory`): in-memory isolated `createMcpAdapter({config})` (NEVER the package's default/ambient export, NEVER `configPath`), registered as an inline `extensionFactories` entry (loads despite `noExtensions`), with the `mcp` proxy tool named into the `tools` allowlist. Confined purposes resolve NO_GRANT and construct nothing. **Sessions must be `dispose()`d, not just aborted** — the adapter tears its child processes on `session_shutdown`, which `abort()` never fires. The package entry is TypeScript-only, so it loads through `jiti` (pinned to the SDK's 2.7.0); its `pi-tui`/`typebox` peers are pinned at the root because `pi-coding-agent`'s shrinkwrap nests the real copies. Skills remain grant-loaded; only the per-change remote-*write* execution behind `confirmRemoteChange` and a user-facing interactive-session surface remain deferred.
- A skill can be imported from a local folder **or a GitHub URL** (`src/main/skills-github.ts`): a pure parser recognises `owner/repo` / `github.com/<owner>/<repo>` with an optional `/tree/<ref>/<subdir>` (the FIRST segment after `/tree/` is the ref — slash-containing branch names are the documented limitation), the archive comes from the GitHub API over global `fetch`, and a built-in ustar reader (`node:zlib`, no `git` binary, no tar dependency) **refuses** absolute/`..` entry paths and enforces download/extraction caps before `importSkillFolder` does the one shared validation+copy. Tests replace the download through `setGitHubFetcher` (same seam pattern as `setSessionFactory`); the handler is registered via `handleCommand` so its refusal codes arrive localized.
- Alarms: `tasks.alarm_at` is the single source of truth; `AlarmScheduler` (`alarms.ts`) is Electron-free (the notifier is injected), firing consumes the alarm, completion cancels it.
- My Day rollover (`rolloverMyDay` in `tasks.ts`) runs on startup: completed My Day tasks clear, incomplete persist.
- The spec source of truth is `specs/` (Spec Kit: `/speckit-specify` → `/speckit-clarify` (optional) → `/speckit-plan` → `/speckit-tasks` → `/speckit-implement`), and `.specify/memory/constitution.md` is the governing constitution — v1.0.0, ratified 2026-09-28, when the previous spec history was cleared and the process restarted. Update specs alongside code changes — the constitution requires it. A plan MUST annotate each feature's deterministic / AI-driven split and every AI step's degradation path (Principle II); core components require headless unit tests before the feature counts as complete (Principle IV).
- Do not add git operations to the knowledge base in v1 — the per-run `.history/` snapshots ARE the undo story (FR-020): each curation keeps its own retained state, and undo restores from the run's own snapshot.
